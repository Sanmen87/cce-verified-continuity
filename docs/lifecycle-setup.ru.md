# Как включить lifecycle CCE в Pi

Руководство для **CCE 0.1.0-alpha.1 и Pi 1.5.0**. Lifecycle сохраняет требования пользователя и историю действий, готовит ограниченный handoff при compaction и восстанавливает обязательное состояние перед продолжением работы. Подробную историю модель запрашивает отдельно. Установка расширения сама по себе этого не включает: по умолчанию CCE работает в `observe-only`, lifecycle выключен.

## 1. Подготовить Pi

Нужны Node.js **>=22.19.0**, npm, Git, ripgrep и установленный Pi. Проверьте в терминале:

```sh
node --version
npm --version
git --version
rg --version
pi --version
```

В PowerShell используйте `npm.cmd` и `pi.cmd`, если политика выполнения блокирует `.ps1`. Менять execution policy не требуется.

Настройте в Pi рабочую модель. Для локальной LLM её сервер должен быть доступен, а указанное в Pi контекстное окно должно соответствовать фактически загруженному окну модели. Конфиг CCE не меняет окно, GPU offload, KV-cache или настройки генерации.

В примерах ниже `-e npm:…` загружает опубликованное расширение на один запуск, не добавляя его в постоянные настройки Pi. Этот способ поддержан в [официальной документации Pi 1.5.0](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/docs/packages.md#install-and-manage-packages). При первом запуске нужен доступ к npm для загрузки пакета.

Если CCE уже подключён через настройки Pi, локальный checkout или VS Code, используйте **один источник расширения**. Не добавляйте npm-копию поверх отдельно подключённой локальной копии. Для уже установленного npm-пакета можно заменить `-e npm:…` на `-e ./node_modules/@sanmen87/pi-extension`; для собранного checkout — на `-e ./packages/pi-extension`.

## 2. Создать конфиг

В корне **проекта, над которым будет работать агент**, создайте `cce.lifecycle.json`. Готовый файл: [examples/lifecycle/cce.lifecycle.json](../examples/lifecycle/cce.lifecycle.json). Содержимое:

```json
{
  "mode": "assist",
  "assist": { "strategy": "combined" },
  "retrieval": { "backend": "hybrid-native" },
  "hybrid": { "enableVector": false },
  "quality": { "coverageEnabled": true, "guardEnabled": true },
  "lifecycle": {
    "enabled": true,
    "ledgerEnabled": true,
    "projectionEnabled": true,
    "historyRecallEnabled": true,
    "capabilityContractEnabled": true,
    "recoveryPolicy": "verified-state",
    "compactionMode": "deterministic",
    "handoffBudgetTokens": 12000,
    "recoveryReserveTokens": 2048,
    "currentWorkEnabled": true
  }
}
```

Это строгий JSON: без комментариев и запятых после последнего поля. Неизвестные ключи отвергаются. CCE не ищет такой файл автоматически; путь явно выбирает пользователь через `CCE_CONFIG`.

| Настройка | Что включает |
|---|---|
| `mode: "assist"` | Разрешает помощь CCE; в `observe-only` CCE не подменяет native compaction |
| `assist.strategy: "combined"` | Инструменты и автоматический retrieval; это отдельный механизм от lifecycle recovery |
| `retrieval.backend: "hybrid-native"` | Локальный AST/FTS-поиск; векторный поиск в примере выключен |
| `quality.coverageEnabled`, `quality.guardEnabled` | Учёт явного контракта и покрытия; сами по себе не запускают тесты |
| `lifecycle.enabled`, `ledgerEnabled` | Lifecycle и журнал исходных событий |
| `projectionEnabled`, `historyRecallEnabled` | Проекция активного контекста и доступ к подробной истории |
| `capabilityContractEnabled` | Объяснение модели возможностей и границ CCE, включая доступность проверок |
| `recoveryPolicy: "verified-state"` | Восстановление требований и Task State с происхождением и свежестью подтверждений |
| `compactionMode: "deterministic"` | Сборка handoff без дополнительной LLM; при невозможности — native fallback |
| `handoffBudgetTokens: 12000` | Верхний бюджет handoff, дополнительно ограниченный доступным контекстом |
| `recoveryReserveTokens: 2048` | Резерв для последующей доставки recovery; не размер всего окна |
| `currentWorkEnabled: true` | CWS: представление текущей работы и рекомендации следующего действия |

Остальные параметры сохраняют значения по умолчанию. Mini-LLM и внешнее хранение больших tool outputs этим примером не включаются. Числа `12000` и `2048` — ограничения, а не обещание такого объёма при каждом запросе. CCE учитывает сведения адаптера об окне, сохраняемый хвост истории и накладные расходы. При отсутствии точного счётчика расчёт остаётся оценочным.

## 3. Запустить Pi из этого же терминала

Сначала перейдите в корень рабочего проекта. В PowerShell:

```powershell
$env:CCE_CONFIG = (Resolve-Path ./cce.lifecycle.json).Path
pi.cmd -e npm:@sanmen87/pi-extension@0.1.0-alpha.1
```

В Bash на Linux/macOS:

```sh
export CCE_CONFIG="$PWD/cce.lifecycle.json"
pi -e npm:@sanmen87/pi-extension@0.1.0-alpha.1
```

Путь может содержать пробелы. `CCE_CONFIG` — переменная окружения процесса, а не поле в `settings.json` Pi. Уже запущенный Pi не получит переменную из другого терминала. Для первого включения и после смены выбранного файла закройте Pi и запустите заново этими командами. Если тот же файл уже выбран, после его редактирования можно выполнить `/reload`; перезапуск также подходит.

CCE хранит состояние в `.context-engine/` внутри рабочего проекта. Добавьте этот каталог в `.gitignore`, если его там ещё нет: история может содержать исходники и пользовательские сообщения. Конфиг можно хранить в Git, если он не содержит приватных настроек.

## 4. Проверить подключение

В редакторе Pi выполните:

```text
/cce-status
```

Ожидайте `mode: "assist"` и `enabled: true`. Статус индекса должен соответствовать выбранному проекту и backend. Эта команда **не выводит все lifecycle-флаги** и сама по себе не подтверждает успешную compaction.

Введите `/cce-continuity-` и проверьте наличие команд `cce-continuity-save` и `cce-continuity-resume` в подсказках Pi. Они регистрируются при включённом lifecycle; выполнять их только ради проверки не нужно. Модели доступны инструменты `cce_search`, `cce_expand`, `cce_history`, `cce_project_state`. Названия инструментов — не slash-команды.

Для проверки механизма без модели и без настройки своего проекта есть [короткий demo](../examples/continuity/README.md), запускаемый из checkout CCE:

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm run demo:continuity
```

Demo использует настоящую compaction Pi SDK, но реплики и изменения кода заданы скриптом. Он не доказывает, что ваша модель самостоятельно продолжит задачу.

## 5. Как работать и что происходит при compaction

1. Передайте Pi задачу и ограничения обычным сообщением. Например: «Добавить архивирование контактов. Сохранить tenant isolation. Не удалять исходные записи». Пользовательские сообщения сохраняются в Ledger автоматически; добровольный вызов `cce_history` для сохранения цели не нужен.
2. Продолжайте работу. Для структурированного учёта отдельных требований можно дополнительно задать явный контракт через `/cce-task-contract` — пример ниже.
3. При естественной compaction Pi вызывает CCE. Для ручной проверки после накопления истории используйте `/compact` **без дополнительных инструкций**. CCE пытается подготовить handoff, сохраняя native хвост и пары tool-call/tool-result. Исходная история не стирается.
4. Перед следующим запросом к модели CCE добавляет обязательное recovery с актуальным Task State. Подробные события и исходники доступны по запросу. Не нужно заново вводить исходный контракт после каждой compaction.
5. Оцените дальнейшие действия агента и выполните независимые тесты. Доставка состояния не гарантирует правильного решения, завершения задачи или отсутствия цикла рассуждений.

Первый явный контракт можно задать одной строкой в редакторе Pi:

```text
/cce-task-contract {"id":"contacts-archive","source":"user","text":"Добавить архивирование контактов. Сохранить tenant isolation. Не удалять исходные записи.","requirements":[{"id":"archive","clause":"Добавить архивирование контактов.","needs":[],"checks":[]},{"id":"tenant","clause":"Сохранить tenant isolation.","needs":[],"checks":[]},{"id":"retain","clause":"Не удалять исходные записи.","needs":[],"checks":[]}]}
```

`clause` должна точно входить в `text`. Здесь `checks: []`: проверки к требованиям не привязаны, поэтому **VERIFIED_PASS не ожидается**. Этот пример задаёт первый контракт; он не является способом бесшумно заменить уже подтверждённую версию требований. Для проверяемых receipts host должен отдельно зарегистрировать разрешённые проверки и их соответствие требованиям. Конфиг не открывает произвольный shell и не регистрирует такие команды автоматически. Обычный Bash-вывод тестов остаётся наблюдаемым результатом; утверждение модели «тесты прошли» не создаёт receipt. После изменения файлов старое подтверждение может стать STALE.

### Как отличить handoff CCE от native fallback

Адаптер пишет в stderr строки с префиксом `CCE_LIFECYCLE_DIAGNOSTIC`. Внутри JSON:

| Поле/значение | Как читать |
|---|---|
| `outcome: "CCE_HANDOFF"` | CCE подготовил свой handoff; это ещё не подтверждение применения |
| `outcome: "NATIVE_FALLBACK"` | Compaction передана Pi; смотрите `reason`, это не успешный CCE handoff |
| `outcome: "OBSERVE"` | CCE наблюдает, не заменяя native compaction |
| `budget`, `budgetInputs` | Рассчитанная capacity, окно модели, резервы и источник подсчёта |

Факт завершения записывается отдельно в Ledger: событие `COMPACTION_COMPLETED` содержит `fromExtension`, а последующий аудит `CONTEXT_RESTORED` — `AUDITED_HANDOFF` либо `UNVERIFIED_NATIVE_SUMMARY`. Эти события можно исследовать через инструмент `cce_history`. В этой версии stdout/stderr-диагностика подготовки и Ledger завершения — разные источники: одна строка `CCE_HANDOFF` ещё не доказывает применение.

Недостаточный бюджет, слишком большой сохранённый хвост, дополнительные инструкции в `/compact` или ошибка сборки могут привести к fallback. Даже подтверждённая compaction не доказывает, что модель использовала восстановленные сведения: для этого нужны фактический provider payload, действия модели и результат независимой проверки.

## 6. Возобновление и новая сессия

Для продолжения **той же** сохранённой сессии запустите Pi с тем же `CCE_CONFIG`, источником расширения и `--continue`, либо используйте `/resume`. Файлы проекта и `.context-engine/` должны сохраниться. CCE восстанавливает состояние и перепроверяет доступные привязки; старый PASS не становится свежим от самого факта открытия сессии.

Переход в **новую чистую** сессию — отдельная явная операция. После задания контракта с ID `contacts-archive` в сессии A выполните `/cce-continuity-save contacts-archive` и сохраните выданный JSON-handle. В чистой сессии B того же проекта, с тем же конфигом, выполните `/cce-continuity-resume ` и вставьте handle целиком. Исходное состояние должно оставаться доступным, а проверки требуют обновления. Это не импорт всей native истории и не подтверждение переноса в произвольный другой агент. Команда `/cce-resume` работает с другим, прежним форматом checkpoint и не заменяет `cce-continuity-resume`.

## 7. Как выключить

Чтобы отключить **только CWS**, задайте `lifecycle.currentWorkEnabled: false` и перезагрузите расширение. Контракт, Ledger и обязательный recovery остаются.

Чтобы вернуть стандартный **observe-only с выключенным lifecycle**, закройте Pi и удалите переменную в том же терминале:

PowerShell:

```powershell
Remove-Item Env:CCE_CONFIG -ErrorAction SilentlyContinue
pi.cmd -e npm:@sanmen87/pi-extension@0.1.0-alpha.1
```

Bash:

```sh
unset CCE_CONFIG
pi -e npm:@sanmen87/pi-extension@0.1.0-alpha.1
```

Это не удаляет `.context-engine/` и сохранённые сессии. Если сторонний host передаёт CCE конфиг программно, менять нужно его настройки: такой конфиг имеет приоритет над `CCE_CONFIG`.

## Если не заработало

| Симптом | Что проверить |
|---|---|
| `/cce-status` неизвестна | Расширение не загрузилось: проверьте выбранный `-e`, версию Pi и ошибки загрузчика |
| Статус показывает `observe-only` | `CCE_CONFIG` должен быть задан до запуска именно этого процесса; файл не обнаруживается автоматически |
| Есть статус, но нет `cce-continuity-*` | Проверьте `lifecycle.enabled`, `ledgerEnabled` и отсутствие второй копии расширения |
| `CCE unavailable` | Валидность JSON и ключей, путь к файлу, доступность SQLite и `rg`; исправьте и перезапустите Pi |
| После редактирования ничего не изменилось | Выполните `/reload` для уже выбранного файла или перезапустите Pi из настроенного терминала |
| Только native compaction | Проверьте `mode`, `compactionMode`, `reason` в диагностике и доступную capacity; большой хвост не всегда помещается |
| Требования есть, но проверки `NOT_CHECKED` / `UNKNOWN` | Без зарегистрированной host-approved проверки это ожидаемо; не просите модель объявить PASS |
| MCP работает, но recovery нет | MCP предоставляет retrieval, lifecycle в этой alpha реализован Pi-адаптером |

Общие инструкции: [QUICKSTART](../QUICKSTART.md). Поведение команд Pi: [официальное руководство](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/docs/usage.md).
